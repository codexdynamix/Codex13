# 55. FINAL NON-NEGOTIABLE RULES

The following rules override convenience:

**RULE 1: DO NOT REBUILD CODEX DYNAMICS FROM SCRATCH.**

**RULE 2: PRESERVE EXISTING FUNCTIONALITY.**

**RULE 3: ONE CUSTOMER = ONE CLIENT.**

**RULE 4: ONE CUSTOMER = ONE CLIENT ID.**

**RULE 5: THE CUSTOMER'S STAGE CHANGES; THE CUSTOMER IDENTITY DOES NOT.**

**RULE 6: DO NOT CREATE A SECOND CUSTOMER WHEN THE CUSTOMER BECOMES ACTIVE.**

**RULE 7: DO NOT CREATE A SECOND CUSTOMER WHEN PORTAL ACCESS IS ENABLED.**

**RULE 8: DO NOT CREATE A SECOND CUSTOMER WHEN A PROJECT IS CREATED.**

**RULE 9: DO NOT CREATE A SECOND CUSTOMER FOR ACCOUNTING, SUPPORT, WEBSITES, DOMAINS, HOSTING, MAIL, OR OTHER MODULES.**

**RULE 10: ALL BUSINESS DATA MUST ULTIMATELY REFERENCE THE SAME CLIENT IDENTITY.**

**RULE 11: PERSISTENT BUSINESS DATA MUST BE STORED IN THE API/DATABASE.**

**RULE 12: DO NOT USE LOCAL STORAGE AS A SECOND BUSINESS DATABASE.**

**RULE 13: DO NOT REMOVE LEGITIMATE CLIENT-SIDE UI STATE.**

**RULE 14: DO NOT BLINDLY DELETE LEGACY CODE BEFORE TRACING ITS DEPENDENCIES.**

**RULE 15: DO NOT CREATE DUPLICATE DATABASE SYSTEMS.**

**RULE 16: DO NOT CREATE DUPLICATE API SYSTEMS.**

**RULE 17: DO NOT PERMANENTLY MAINTAIN TWO DIFFERENT CUSTOMER TERMINOLOGIES FOR THE SAME ENTITY.**

**RULE 18: THE FINAL ACTIVE APPLICATION MUST USE CLIENT TERMINOLOGY CONSISTENTLY.**

**RULE 19: RENAME CUSTOMER-RELATED CODE, FILES, COMPONENTS, FUNCTIONS, VARIABLES, TYPES, ROUTES, DATABASE STRUCTURES, AND UI REFERENCES AS PART OF THE MIGRATION.**

**RULE 20: DO NOT LEAVE THE OLD CUSTOMER CONCEPT AS AN ALTERNATIVE NAME FOR CLIENT IN THE FINAL ACTIVE CODEBASE.**

**RULE 21: DO NOT PERFORM A BLIND GLOBAL TEXT REPLACEMENT. UNDERSTAND EACH REFERENCE BEFORE RENAMING IT.**

**RULE 22: MIGRATE EXISTING DATA SAFELY.**

**RULE 23: NEVER DESTROY EXISTING BUSINESS DATA TO MAKE THE MIGRATION EASIER.**

**RULE 24: TEST THE COMPLETE CLIENT LIFECYCLE.**

**RULE 25: DO NOT CLAIM COMPLETION WITHOUT ACTUAL VERIFICATION.**

The final objective is a single coherent Codex Dynamics architecture in which the entire application understands and manages one customer entity: **Client**.

The Client has a lifecycle stage.

The Client has portal access or does not.

The Client owns projects, websites, domains, hosting, accounting records, support records, files, communication, and other business information.

But all of those relationships ultimately belong to the SAME Client.

There must not be two competing customer identities for the same person or company.

There must not be two competing customer-management systems.

There must not be a browser-only business-data system competing with the database.

And the finished application must consistently use the Client concept throughout its active frontend, backend, API, database, UI, types, functions, routes, and related architecture.

Preserve the existing Codex Dynamics application.

Correct the architecture.

Migrate the existing data safely.

Rename the customer architecture consistently.

Remove duplicate customer identities.

Move persistent business data to the API/database.

Test everything affected.

Do not rebuild the project.
